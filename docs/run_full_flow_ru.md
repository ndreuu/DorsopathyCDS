## Открыть приложение

```sh
cd /Users/andrew/Projects/DorsopathyCDS
PYTHONPATH=src python3 -m dorsopathy_platform serve --store var/multimodal --port 8766
```

Для уже запущенного сейчас сервера доступен [свежий настоящий SPIDER-пример](http://127.0.0.1:8766/#run=run-e0960ab7706b4a92bb0dea2e93871352).
Его ID и аудит сохранены локально в `var/latest-live-example.json`. Ссылка относится
к текущему store; новый пустой store не содержит этот run.

Откройте <http://127.0.0.1:8766/> и нажмите **«Запустить пример всех модулей»**.
Программа создаёт эпизод, загружает синтетические исходные данные, запускает восемь
провайдеров и сохраняет результаты, изображения, snapshot и отчёт. Каждый запуск
имеет собственные задания; MRI обрабатывается в отдельной очереди.

Это расчёт по исходным пикселям, геометрии и отсчётам сигнала. У первого отчёта
будет результат «Недостаточно данных»: соответствие MRI клинике ещё не оценено.
Кнопка **«Добавить учебное подтверждение и обновить отчёт»** создаёт новую
синтетическую врачебную оценку конкретного MRI-результата. MRI повторно не считается;
первый отчёт остаётся доступным по старому run ID. Учебная оценка не является
автоматической интерпретацией изображений.

регистрации всех модальностей пока нет. Сопоставление проверяет пригодность входов;
оно не выдаёт процент достоверности диагноза и не исключает дорсопатию.

## Запустить без браузера

```sh
PYTHONPATH=src python3 -m dorsopathy_platform run-flow \
  --store var/cli-example --output var/cli-example-report.json
```

`run-flow --manifest PATH --idempotency-key KEY` запускает выбранные модули
по CaseManifest: ссылки должны уже принадлежать этому эпизоду. Повтор того же
ключа и manifest возвращает тот же run; изменение manifest с тем же ключом — конфликт.
Один store обслуживает один контроллер. Для CLI параллельно с сервером используйте
другой store либо HTTP API сервера.

## Настоящий MRI

Нормализатор читает существующий экспорт MRI backend/SpinoSarc в отдельном окружении
с imaging-зависимостями и сохраняет `bundle.json`, связанные файлы и
`upload-manifest.json`. Затем:

```sh
PYTHONPATH=src python3 -m dorsopathy_platform import-bundle \
  /путь/к/нормализованному/bundle --store var/mri-replay
```

Это **replay**: новый inference не запускается. Файлы проверяются по размерам/SHA,
импортируются в новый эпизод, затем измерения и изображения пересчитываются.
Без подтверждённой связи с осмотром результат клинического правила остаётся unknown.

Для нового TSS inference нужен trusted worker-конфиг, переданный при старте сервера
через `--mri-config var/mri-worker.json`. Формат — объект с `command` (массив argv)
и `timeout_seconds`; команды и локальные пути HTTP не принимает. Точная инструкция,
окружения и ограничения форматов приведены в `docs/mri_provider_ru.md`.
В форме загрузки для live MRI передайте один поддержанный объём и параметры
`{"processing_mode":"live"}`. Режим в CaseManifest сам по себе не запускает модель.

Проверенный свежий прогон использовал открытый SPIDER `246_t2.mha`, локальные
веса TSS r20260730 и MPS. Получены AP-размеры канала и объёмы масок дисков по пяти
уровням. Площадь канала на сагиттальном native-plane входе оставлена `not_assessed`;
нумерация требует подтверждения. Прямой worker-прогон занял около 94 секунд;
повтор через HTTP-приложение — около 92 секунд. Это не оценка производительности
на произвольных исследованиях.

## Проверяемый результат

`GET /runs/{id}/report` возвращает неизменяемый JSON с выбранными результатами,
источниками каждого врачебного факта, неизвестными данными и сохранённой редакцией
каталога. `GET /runs/{id}/report.html` показывает те же данные и прямые цитаты.
Исходные и полученные файлы доступны по scoped URL
`/episodes/{episode}/artifacts/{artifact}` с проверкой SHA/size.

Исследовательские материалы лежат в `research/`, программа в `src/`, реальные
входы/веса/отчёты в игнорируемом `var/`. Тесты проверяют поведение программы;
клиническая валидация и регистрация ПО остаются отдельной работой.
